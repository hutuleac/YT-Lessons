What to do

The ticket needs a visible finish line

A vague prompt makes the agent guess what matters, and once it's guessing you're no longer managing the work, you're cleaning it up — a real ticket names the scope and the finish line.

The ticket needs a visible finish line

  1. "Make the app better" forces the agent to guess. Guessing means you clean up later.
  2. A ticket needs: the job, the scope, the expected experience, the boundary.
  3. Plan mode first: inspect the repo, propose the approach, wait for approval.
  4. Then implement as one focused, reviewable change — not a pile of everything at once.

What to do

  • Write the ticket the way you'd brief a new hire: job, scope, expected experience, and what's off-limits — not "make it better."
  • Run plan mode before implementation on anything that isn't trivial — the ask is inspect first, propose second, wait for approval third.
  • If a ticket is big enough that you can't review the diff in one sitting, it's not one ticket.

Give the agent eyes

  1. A landing page can load fine and still feel confusing. Code review won't catch that.
  2. Eyes means: open it, click through it, check console and network, judge it as a user.
  3. Ask it to judge from a named persona's first five seconds, not just "does it work."
  4. Then make one focused pass on the highest-impact issue it finds — not a rewrite.

Must-fix, should-fix, okay-to-ship

  1. Once the agent builds fast, the bottleneck moves to judgment, not output.
  2. Layer one: your own read of the diff. Does it match the ticket? Anything surprising?
  3. Layer two: the agent reviews itself against review.md, a written standard.
  4. Sort findings into must-fix, should-fix, okay-to-ship — not just "looks good."

What to do

  • Write review.md once, as the explicit standard changes get judged against — not a one-off instruction typed into each review prompt.
  • Sort every review pass into must-fix / should-fix / okay-to-ship rather than a single verdict.
  • Treat an unexpected file in the diff as the review's first question, before reading anything else.
  • Run a deeper, fresh-context review pass on high-stakes changes — auth, payments, data.

Scheduled routines

Scheduled routines

  1. Every business has boring, recurring work: read notes, spot patterns, flag risks.
  2. Start there, not with unsupervised production code.
  3. Morning brief: read customer notes and issues, write one page, don't touch code.
  4. Weekly review: group issues, name the week's highest-leverage fix, don't touch code.

What to do

  • Start scheduled work with a read-only routine — no code edits, no pull requests — before trusting an agent with anything that ships.

One session, one assignment

Worktree-isolated sessions let several agents work at once without their changes mixing — but only if each session gets one clear job, or you end up with a pile of tangled work to sort out at the end of the day.

One session, one assignment

  1. Separate sessions, separate worktrees — changes stay isolated instead of mixing.
  2. One session, one clear assignment, one specific handoff format.
  3. Different job types in parallel: a bug fix, a copy change, a sales asset.
  4. The goal is small packets you can review, not one big pile to untangle.

What to do

  • Before starting parallel sessions, write one specific handoff format per session — what it should come back with, not just what it should do.
  • Mix job types across sessions (bug fix, copy, sales asset) rather than three variations on the same task — that's what actually benefits from isolation.
  • Review and merge each session's output separately; don't let three sessions' changes pile up before you look at any of them.

Three tiers of permission

Split what an agent can do into safe, ask-first, and human-owned — the same delegation model you'd use for a new hire, so autonomy grows with trust instead of being all-or-nothing.

Three tiers of permission

  1. Safe: read files, run local tests, edit a small branch, draft a PR. No approval needed.
  2. Ask first: install dependencies, touch migrations, auth, or payment logic, delete files.
  3. Human-owned: production deploys, customer data, billing, security-sensitive changes.
  4. Start conservative. Loosen the tier as the repo brain and review checklist get stronger.

What to do

  • Write down which actions fall in each tier before turning an agent loose on a repo — don't decide it live, mid-task.
  • Keep production deploys, customer data, and billing decisions human-owned no matter how much autonomy the agent has earned elsewhere.
  • Start conservative and use plan mode plus manual review for anything new, then loosen as trust and tooling (routines, review checklist) mature.

Skills, connectors, and hooks

Three different jobs get confused under "make the agent smarter" — a skill makes a prompt repeatable, a connector gives it access to a tool, a hook enforces a rule automatically. Naming which one you need keeps the setup from turning into one big pile of instructions.

Skills, connectors, and hooks

  1. Typing the same prompt repeatedly? That's a skill — save it, reuse it.
  2. Need GitHub, Linear, Drive, Slack context? That's a connector — access, not instructions.
  3. Need formatting or tests to run automatically? That's a hook — a rule, not a request.
  4. Skills make work repeatable. Connectors give context. Hooks make the workflow safer.

What to do

  • Before writing a new instruction, ask which of the three it actually is — a repeatable task (skill), a data source (connector), or a rule that must always fire (hook).
  • Turn a prompt into a skill the second time you type a version of it, not the fifth.
  • Put anything that must always happen — formatting, tests before a PR — in a hook, not in a prompt you might forget to add.

The whole loop

Customer feedback goes into /customers. Direction goes into roadmap.md. Working style goes into claude.md. Standards go into review.md. Small tasks go through plan mode. Changes go through preview and review. Recurring work becomes a scheduled routine. None of these pieces is impressive alone — the leverage is in running them as one loop instead of reaching for whichever one you remember that day.
