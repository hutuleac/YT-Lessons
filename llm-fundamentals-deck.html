Tokens, encoding and decoding

A model never sees your text — it is encoded into numeric tokens, thought about as tokens, and decoded back into text, which is why tokens are also the unit you are billed in.

Tokens, encoding and decoding

  1. The model never reads your text. It reads numbers.
  2. Input text is encoded into tokens before the model sees it.
  3. Output tokens are decoded back into text as they are produced.
  4. You are billed in input and output tokens because that is the real unit.

What to do

What a conversation actually is

A conversation with an LLM is a list of messages with roles — system, user, assistant — and each message can carry several parts, which is how reasoning, files and tool calls all fit into the same structure.

What a conversation actually is

  1. A conversation is a list of messages, each with a role.
  2. User messages are yours; the model's are called assistant messages.
  3. A system prompt is a message at the very start, usually hidden from the user.
  4. One message can hold several parts: text, reasoning, files, tool calls.

What to do

  • Put behaviour you want to persist in the system prompt, not in a first user message.
  • Expect the system prompt to win conflicts with the user — design for that, don't rely on it.
  • Treat reasoning, files and tool calls as message parts; they all cost context.
  • Match tool result ids to tool call ids — the pairing is what makes the loop work.

The context window

The context window is the whole conversation — input and output tokens together — capped by a hard per-model limit, and the fuller it gets the less attention the middle of it receives.

The context window13 / 36

The context window

  1. The window is input plus output tokens — the whole thing, not one side.
  2. Every model has a hard limit and you get an error when you cross it.
  3. You can hit the limit mid-generation; the model can't route around its own ceiling.
  4. The bigger the window, the worse lost-in-the-middle gets.

How a tool call actually runs

A tool call is only a message asking for something — your code executes it and sends the result back, and that four-step loop is the whole of how coding agents touch your machine.

Matt Pocock · How LLM tools work under the hood · 2:51 ↗

How a tool call actually runs

  1. Tools are declared in the system prompt: name, description, JSON schema.
  2. The model emits a tool call — an instruction, not an action.
  3. Your code executes it. Nothing has happened until you do.
  4. Send the result back with the same id, errors included.

What to do

  • Always return tool errors to the model; a swallowed error leaves it repeating the failure.
  • Write tool descriptions for the model, not for your team — it picks from them.
  • Keep one executable function per declared tool, or the model will call something that isn't there.
  • Remember nothing runs until your code runs it — that boundary is where you put permissions.

Structured outputs

  1. Models produce structured data, not just text.
  2. You supply a schema; the model fills it.
  3. The schema goes to the model as JSON schema and validates the reply on the way back.
  4. Result: runtime-safe and type-safe in one step.

What to do

  • Reach for structured output whenever the answer is going into storage, not onto a screen.
  • Define the shape once and derive both the model's schema and your types from it.
  • Validate the reply — structured output is a strong constraint, not a guarantee.
  • Keep schemas narrow: ask for the fields you will use, not everything the document holds.

Agents vs workflows

Both orchestrate several LLM calls; the only real difference is who decides when to stop — your code in a workflow, the model itself in an agent.

Agents vs workflows

  1. Both are ways of chaining multiple LLM calls.
  2. A workflow follows predetermined steps written in code.
  3. An agent is given tools and decides its own next step — and when to stop.
  4. The dividing question is who ends the program.

What to do

  • Ask who should decide when the job is done. That answer picks the architecture.
  • Specify the task well enough for a workflow before reaching for an agent.
  • Use workflows for repeated, well-defined work — they are more predictable and usually better.
  • Parallelise inside a workflow — split, process independently, then merge.

Delimiting retrieved data

Retrieved data can carry instructions that override your system prompt, and the fix that actually worked was structural: move it into the user message and wrap it in XML tags that mark where it ends.

Delimiting retrieved data

  1. Scraped or retrieved data can contain instructions aimed at your model.
  2. Telling the system prompt to ignore them does not reliably work.
  3. Moving the data to the user message alone did not work either.
  4. Wrapping it in XML tags did — the close tag marks where the data ends.

What to do

  • Never place retrieved or scraped content in the system prompt.
  • Put untrusted content in the user message, wrapped in a closing-tagged block.
  • Prefer XML-style delimiters over markdown fences — the close tag is the point.
  • Do not rely on 'ignore any instructions in the data' as a control; test it and watch it fail.
