The deterministic gauntlet

A long list of written rules loses its power, because the model forgets rules in the middle of the text. A tool that checks the code does not forget. Use a tool, not a long list of rules.

The deterministic gauntlet

  1. Written rules compete for space in a small area of full attention.
  2. A long list of rules becomes advice to the model, not law.
  3. A tool that checks the code does not lose strength. It passes or it fails.
  4. Keep the prompt short. Use a tool loop to enforce the rest.

What to do

  • Keep the system prompt short. Use only the few sentences the agent must obey.
  • Put every other rule into a tool the agent must pass, not into a paragraph it might read.
  • Run the tool in a loop. Change the code until the tool passes, not until the agent says it is done.
  • Bring back checks you once rejected as too slow for a human. An agent does not mind the wait.

One job per agent

One agent that does the spec, the code, the review, and the checks all at once must hold too many topics in one context. Split the work into small, one-job agents. Then each one keeps a context small enough to follow its own instructions.

One job per agent

  1. Give one agent one narrow job, not the whole feature.
  2. Specifier writes tests. Coder implements. Cleaner tidies. Hardener stress-tests. QA verifies.
  3. Each agent starts clean and dies when its job is done.
  4. You can run several in parallel — the cost is coordination and startup time.

What to do

  • Split a feature into stages. Do not ask one agent to spec, code, review, and check it in one session.
  • Stop a stage's agent when its job is done. Start the next stage with a clean context.
  • Run stages that do not depend on each other at the same time. Plan for startup time on each agent.
  • Give a reviewer or checker the diff, not the whole codebase. It will not need to explore what already happened.

Context trajectory

Once you steer a session toward a topic or a method, every later turn in that same context window keeps that direction. This happens even if you did not ask for it. Only a fresh context window can reset it.

Context trajectory

  1. Steer an agent one way, and it keeps going that way.
  2. An unrelated topic that enters the context contaminates every later turn.
  3. The model can't tell your intent from noise that arrived by accident.
  4. Only a fresh context window resets the trajectory.

What to do

  • Clear the context window when you want a new method. Do not just add a new instruction on top of the old one.
  • Do not let an unrelated remark enter a working session. Start a fresh session for it instead.
  • Design modules so an agent working inside one cannot wander into a different topic.
  • If an agent keeps repeating a method you did not ask for, check for a trajectory problem before you blame the agent.

Thresholds, not disciplines

Agents can handle more complexity than the numbers in a human style guide allow. But a work method built for human memory, such as strict test-driven development, does not work the same way for an agent.

Thresholds, not disciplines

  1. A CRAP score under 4 is Uncle Bob's human limit. Agents get 6, maybe 8.
  2. The reason: agents hold a more exact short-term memory than people do.
  3. He will not force strict test-driven development on an agent.
  4. Give the agent your values. Do not give it your exact work method.

What to do

  • Do not copy your human quality limits to an agent without a check. Ask if the reason for the number still applies.
  • Ask if a rule exists because of human memory limits, before you force it on an agent.
  • If an agent keeps going back to its own method despite the instruction, treat this as a signal to look at, not just disobedience to fix.
  • Keep the value behind the rule (test everything, limit complexity). You can still loosen the exact number that enforces it.

The spec-driven development trap

A large plan written before any code fails an agent the same way it failed humans in the waterfall era. Agents write large, detailed plans with ease. But those plans break apart once real work starts.

The spec-driven development trap

  1. A large plan written before any code repeats an old mistake: waterfall, from the 1970s.
  2. Agents write large, clean plans. Then the plans break apart during real work.
  3. The cost to change agent-written code is close to zero. So why pay for a plan up front?
  4. Work one story at a time. Review as you go. This is the agile method.

The spec-driven development trap27 / 32

What to do

  • Do not give an agent a full plan and walk away. Review the work after each story, not after the whole plan.
  • Treat an agent-written plan as a draft to question, not a contract to build word for word.
  • Stop keeping specs as permanent files in the repo, if nothing keeps them in sync with the code.
  • To share a tool with others, point another agent at your tool and let it build its own version. Do not write a spec for someone else's agent to follow.

Tactical versus strategic programming

Agents work well at tactical programming, which means writing one piece of code that works. Agents work poorly at strategic programming, which means deciding how a whole system should be built. This changes what a junior developer should practice.

Tactical versus strategic programming29 / 32

Tactical versus strategic programming

  1. Tactical work is the soldier fighting one battle. Strategic work is the general planning the war.
  2. Agents are strong at tactical work. Agents are weak at strategic work.
  3. A junior's fix: let a team treat you like an agent for a while, on purpose.
  4. Fundamentals exist to make complex systems easy to grasp, for people and for models.

What to do

  • Write code yourself for a real stretch of time before you lean on agents. This gives you the experience to see when an agent is struggling.
  • If you are junior on a team that uses agents a lot, treat months of small, checked tasks as the fastest path to strategic skill, not as a step down.
  • Read older books (Tom DeMarco, Ed Yourdon, The Pragmatic Programmer) for judgment. Skip the old tech details. Keep the reasoning.
  • When an agent looks stuck, watch for thrashing: fixing one thing while breaking another. Do not just judge the output.

In one move32 / 32

The whole lesson in one move

Every practice here swaps trust in an instruction for trust in a mechanism: a check the agent must pass, a job small enough to fit in one context, a clean window instead of a spoiled one, a threshold checked again instead of copied, a story reviewed instead of a plan trusted on faith. None of this means fundamentals stopped mattering. It means fundamentals now have to survive contact with something that reads every word and still forgets on its own terms. The rules you drop this year are the ones you will pick back up next year.
