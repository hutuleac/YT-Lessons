The ticket needs a visible finish line

  1. "Make the app better" forces the agent to guess. Guessing means you clean up later.
  2. Brief it in three parts: the task, the guardrails, what done looks like.
  3. Newer models plan as they work. Check what it did, not what it planned.

What to do

  • Write the ticket the way you'd brief a new hire: job, scope, expected experience, and what's off-limits — not "make it better."
  • Brief in three lines — task: this week's report from the CRM export; guardrails: don't amend the template, don't email anyone; done: every figure matches the export.

Your effort level is too high

  1. Higher effort means more thinking tokens for the same work.
  2. Exploration barely benefits from effort — it just costs more.
  3. Benchmarks hold the task static. You don't have to.

Hand the agent something that can objectively score its own output — a test suite, a screenshot, a simulator — and it stops needing you between attempts, because it can tell for itself whether the last one was closer.

Give it a way to check its work

  1. One pass with no feedback signal gets you "pretty good" and stops there.
  2. An objective check — tests, screenshot, simulator — lets it grade its own attempt.
  3. Two or three self-graded iterations is where pretty good becomes almost perfect.
  4. The check must be machine-readable, not a matter of taste.
  5. "Double-check your work" adds cost. A pass/fail check adds quality.

What to do

The /goal judge only reads the chat

The deterministic gauntlet

A long list of written rules loses its power, because the model forgets rules in the middle of the text. A tool that checks the code does not forget. Use a tool, not a long list of rules.

The deterministic gauntlet

  1. Written rules compete for space in a small area of full attention.
  2. A long list of rules becomes advice to the model, not law.
  3. A tool that checks the code does not lose strength. It passes or it fails.
  4. Keep the prompt short. Use a tool loop to enforce the rest.
  5. ALL-CAPS rules are still requests. A hook is a guarantee.

What to do

  • Keep the system prompt short. Use only the few sentences the agent must obey.

Scheduled routines

  1. Every business has boring, recurring work: read notes, spot patterns, flag risks.
  2. Start there, not with unsupervised production code.
  3. Morning brief: read customer notes and issues, write one page, don't touch code.
  4. Weekly review: group issues, name the week's highest-leverage fix, don't touch code.

What to do
