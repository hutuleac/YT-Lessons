The one-paragraph takeaway

Video Snapshot

  1. 56-minute live interview: Matt Pocock hosts Robert C. Martin ("Uncle Bob", author of Clean Code) on how his agentic coding practice has evolved since he started using AI agents around December 2025.
  2. Central arc: Martin tried steering agents with long prompt documents (TDD rules, clean-code rules) and found models treat written rules as "guidelines, not actual rules" (the Pirates of the Caribbean line) — he abandoned steering for deterministic tools (CRAP score, mutation testing) run in an enforced loop instead.
  3. He resurrected two tools he'd shelved as impractical in the early 2000s — CRAP score (coverage + cyclomatic complexity) and mutation testing — because agents don't care how boring or slow the checks are.
  4. He now runs a 5-stage agent pipeline per feature: specifier -> coder -> cleaner -> hardener -> QA agent, each with a narrow single-purpose context window; a task that takes one agent ~5 minutes with weak results takes the full gauntlet ~1 hour but at much higher quality (roughly 4-5x a human, not 10x).
  5. He explicitly rejects both spec-driven development (upfront heavy planning) and imposing human process disciplines like strict red-green-refactor TDD on agents, favoring an Agile-style iterate-and-feedback loop instead.
  6. Cites the 'lost in the middle' context-window effect and Dex Horthy's 'smart zone / dumb zone' framing as the technical reason steering documents fail once they exceed a few sentences.
  7. Introduces a 'trajectory' concept: whatever direction a context window has been steered toward persists and contaminates every subsequent turn in that session — the only fix is starting a clean context.
  8. Closing argument: software fundamentals (clean modules, small deep interfaces, low complexity) matter more, not less, because AI models are trained on human-organized complexity and hit the same walls humans do past a complexity threshold.
Structural critique PRACTICE SHIFT, DEC 2025-AUG 2026

Prompt-based "steering" documents don't hold — deterministic tools in an enforced loop do

Martin's first instinct was to write Claude.md-style instruction documents ("here's how you do TDD, here's what clean code looks like"); he found models treat that content as soft guidance that decays with context length, not as rules.

  • His early prompts grew into 5-10 page documents describing TDD and clean-code rules; he says models treat those rules "in the Pirates of the Caribbean sense... more like guidelines."
  • Root cause per his own research: 'lost in the middle' — content at the very start and very end of a context window keeps priority, content in the middle gets effectively ignored as the window grows, no matter how important it was when written.
  • Practical implication he draws: trim the initial prompt to its absolute minimum so it stays in the high-priority zone, then enforce everything else with deterministic tools that run after the fact and don't live in the context window at all.
  • Deterministic tools scale where prompted rules don't: you can "layer them up and up" without them competing for context-window priority the way instructions do.
  • He flags the open question honestly: there is a point where enough automated checks slow the agent down below human speed and "you've lost the game" — he hasn't found that ceiling yet, but currently gets roughly a 2-4x productivity margin over an unconstrained agent.
Pull quote
“They definitely will soften... they treat those rules in the Pirates of the Caribbean sense. They're more like guidelines.”— Robert C. Martin
Worth noting

Recommendation TOOLS ORIGINALLY SHELVED AS IMPRACTICAL, c. 2000

Two early-2000s tools he'd abandoned as too slow for humans are now core to his agent harness

CRAP score and mutation testing were both tools Martin tried around the year 2000, found valuable, and shelved because fixing what they found took a human too long to be worth it — agents remove that constraint.

  • CRAP (an acronym for a coverage + cyclomatic-complexity formula) scores how "crappy" a function is; running it over a big project around 2000 surfaced many bad functions, but manually fixing and re-testing them all wasn't worth the time.
  • Mutation testing flips code operators (negative<->positive signs, less-than<->greater-than, equal<->not-equal) and re-runs the full test suite expecting a failure; a passing 'surviving mutant' signals an inadequate test. His year-2000 run took an overnight batch (the suite alone ran 4 minutes, run several hundred times).
  • By December 2025 he started telling agents to run both tools after every change and clean up whatever they flagged — turning a previously impractical overnight process into a routine ~30-minute step.
  • His current goal: reach a point where he doesn't look at the generated code at all, verifying quality instead via CRAP scores staying low, mutation-testing coverage, and periodic spot checks — not code review of every diff.
  • For humans he keeps CRAP scores below 4; for agents he's deliberately widened the threshold to 6 (considering pushing to 8), reasoning agents have a much larger and more accurate short-term memory than humans and can handle more pathways-per-function before losing track.
Pull quote
“These things are fast, and they are, and if I can constrain them to do a good job, then I am not going to impose my slowness upon them.”— Robert C. Martin
Worth noting
The crap-score threshold of 6 (vs. 4 for humans) is Martin's own experimental guess, arrived at partly by debating the number with agents themselves — which he explicitly says not to trust as a source of truth.
Recommendation CURRENT WORKFLOW, ~1HR PER FEATURE

A 5-stage specifier -> coder -> cleaner -> hardener -> QA pipeline, each agent single-purpose and short-lived

Rather than one agent or many loosely-coordinated "specialist" agents with persistent roles, Martin runs a fixed sequential gauntlet where each agent is born, does one narrow task, and dies so the next starts with a clean context.

  • Specifier: turns a human-written document into a Gherkin acceptance test (given/when/then) plus a QA procedure written from a human-at-the-UI point of view.
  • Coder: writes unit tests and the implementation to satisfy the story and make the Gherkin test pass; expected to leave a mess behind.
  • Cleaner: runs CRAP analysis and general code review to clean up the coder's mess.
  • Hardener: runs mutation testing to a target of 100% coverage, described as "absolutely merciless" — this stage takes the longest.
  • QA agent: turns the written QA procedure into an executable script that drives the system and produces a deterministic pass/fail result.
  • Net effect: a task one agent completes in ~5 minutes with 'questionable results' takes the full pipeline about an hour, versus roughly half a day for a human doing equivalent-quality work — a ~4-5x productivity gain with materially higher quality than a human would typically produce.
  • Two structural benefits of splitting into narrow single-task agents: they can run in parallel (his laptop supports more than 3 concurrent coders), and each agent's context window stays small enough that the 'lost in the middle' problem barely applies, so a few more rules can be piled on and actually get followed.
  • Named tradeoff: each new agent has real startup/cold-context overhead (roughly 10-15 seconds plus re-establishing context), and coordinating handoffs between agents has real communication overhead — but he says it's still faster overall than a human by a large margin.
Pull quote
“It's going to mutate it and it's going to have 100% coverage... it's going to do that work, which takes a good long time.”— Robert C. Martin, describing the hardener stage
Worth noting
Martin distinguishes this from large swarms of many differently-"personified" agents (his phrase: agents with their own email accounts) which Pocock says he's skeptical of — this is a narrow, sequential specialization, not a large autonomous org of agents.
Structural critique OBSERVED PATTERN, NOT A CITED STUDY

A context window develops a "trajectory" that contaminates everything after it — the only fix is a clean context

Pocock introduces the term "trajectory": once a session is steered a certain way (e.g., told to test via the UI), every subsequent instruction in that same context window gets pulled toward that same direction regardless of what's actually asked next.

  • Martin agrees and offers an analogy: a person having a calm chat with a model about brewing coffee, interrupted by someone else's unrelated remark about a soap opera getting pulled into context — from that point on, the model can't fully separate the two threads and coffee answers start drifting toward the soap-opera content.
  • Framed as a specific driver of agent hallucination and misalignment distinct from factual hallucination: the model isn't inventing false facts, it's failing to keep threads in the same context window separated.
  • Practical consequence for the pipeline design above: narrow, short-lived, single-purpose agents keep trajectory clean by construction, because each one only ever sees content relevant to its one job before it's discarded.
Pull quote
“As long as you can keep the direction of the model unconfused... it's not going to have these crazy hallucinations that people often deal with.”— Robert C. Martin
Worth noting
This is offered as a well-known effect Martin has personally observed with models and non-programmers alike, not as a named, citable research result.
Recommendation TOOLING IN PROGRESS, ARCHITECTURE ENFORCEMENT PARTIALLY MANUAL

Well-partitioned modules with deep, narrow interfaces are the single biggest lever for agent (and human) performance

Martin argues the same case he's always made for clean module boundaries now applies to agents for an identical reason: both humans and models can only "focus on" a bounded amount of context at once, and a well-scoped module keeps a model's attention from being diluted the same way a bloated one dilutes a human's.

  • Until roughly a month before this interview he did architecture design manually: interrogating agents about existing module relationships, getting alarmed by the answers, then hand-designing the target module structure and handing agents an implementation plan.
  • He had his agents build him a custom UML-style architecture viewer he can use to drill down from system level into modules, sub-modules, and the underlying code on screen — he calls this genuinely useful and uses it regularly.
  • He also built a deterministic dependency-direction checker: a specification file defines which modules may depend on which; a checker enforces it at the end of a run, and violations must be fixed (typically by inverting a dependency, inserting an interface, or splitting a module). He says he's trying, without much luck yet, to automate the design step itself.
  • Explicitly endorses John Ousterhout's 'deep modules' concept (small interface, large hidden implementation) as especially good for agents specifically because a model can act on an interface without reading or understanding what's behind it — both an advantage (efficiency) and a danger (if the implementation and interface silently diverge).
  • Notes models pay attention to code structure and consistency, and also read tests to infer what a system does — so clean structure and a meaningful test suite both function as documentation the agent actually uses.
Pull quote
“Anything that is well partitioned with well-disciplined interfaces between it is something a human can grasp because we compartmentalize in our minds — well, so do the models, so do the agents.”— Robert C. Martin
Structural critique REVISED PRINCIPLE FROM CLEAN CODE ERA

Human process disciplines don't automatically transfer to agents — even when the underlying value does

Asked what he'd revise from Clean Code for the agent era, Martin draws a sharp line between values (which still apply) and disciplines/behaviors (which were designed around specifically human limitations and shouldn't be force-fit onto agents).

  • Strict red-green-refactor test-driven development (write one line of test, one line of code, alternating) is, in his words, a discipline built for human short-term memory limits — he no longer enforces it on agents. Left unconstrained, his agents naturally fall back to writing a whole function then its test (the style he associates with Ousterhout), and he now lets them.
  • General framing he lands on: "it is probably a mistake to impose a human discipline on an agent — it is not a mistake to impose human values on the agent." Values like low complexity and test coverage still apply; the specific human workflow used to get there (strict TDD cadence) does not need to.
  • He also rejects heavy upfront spec-driven development for agents, drawing a direct parallel to 1970s waterfall and the Agile movement's reaction to it: extensive upfront specs sound safe but always fall apart once the agent runs into reality, forcing a stop-rewrite-restart cycle. His own attempt at this the same week as the interview was, in his words, "always a disaster."
  • His alternative is Agile-style iteration: run a story or two, review the resulting architecture, manually intervene if needed, run more stories, repeat — with the expectation that a manual organizing/review step at the end may never fully disappear.
  • Cost-of-change analogy: if changing a house cost a flat $1-5 regardless of when in construction the change happened, no one would pay an architect to front-load a perfect plan — they'd iterate live with the contractor. He argues agentic coding has pushed the cost of software change close enough to zero that the same logic applies, undercutting the case for upfront planning.
  • On "spec-driven development" as a label, Pocock pushes back that its definition is so loose it can describe anything from a one-line Slack request to a full requirements doc; Martin's distinguishing test is whether the specification is persisted and returned to — his own specs are ephemeral by design and get discarded once implemented, with the finished code (plus his open-sourced tools like the CRAP checker and mutation tester) standing in as "the" specification for others to adapt rather than copy directly.
Pull quote
“It is probably a mistake to impose a human discipline on an agent. It is not a mistake to impose human values on the agent.”— Robert C. Martin
Worth noting
Martin explicitly caveats his own long-standing waterfall prediction as one he expects to eventually lose: "that's a prediction I'll probably lose, but still."
Structural critique OPEN QUESTION, NO SETTLED ANSWER OFFERED

AI has eaten tactical programming — Martin's tentative path for juniors to still learn strategic programming

Using Ousterhout's tactical (ground-level, executing) vs. strategic (directing) programming framing, Pocock asks how newcomers learn strategic skill when agents now do most tactical work; Martin admits he doesn't have a confident answer but sketches a path.

  • Step 1: a new programmer should still spend real time (he estimates roughly a year, loosely) writing code by hand, specifically so they understand what the agents they'll later direct are actually dealing with.
  • Step 2: when hired into an agent-heavy team, a junior should be treated by the lead engineer the same way an agent is treated — given the same tasks and subjected to the same deterministic tools/checks agents face — and should expect to spend several months "horribly unproductive" while absorbing judgment.
  • Draws a direct parallel to his own decade-old advice that developers who only ever write high-level languages should spend a weekend writing assembly, purely to remove the feeling that lower layers are unexplainable magic; he extends this into a full stack a learner should pass through: binary, assembly, a language like C, a higher-level language like Python, then agent-directed/deterministic-tool work, and only then strategic agent direction under supervision.
  • On how to recognize agent "struggle" (the signal that told him something was wrong back in December): he says he recognized it from having personally been through the same struggle as a programmer — the risk is a true novice won't recognize the pattern the first time they see it.
  • His reading recommendation for developing the strategic "feel": older, now-unfashionable books, naming Tom DeMarco and Ed Yourdon's work and The Pragmatic Programmer by name, while noting some of their specific advice will be dated (many were written in the 1970s-80s) even though the underlying lessons hold.
  • He frames the accelerated agent feedback loop as an upside for learning speed specifically: because agent cycles are so much faster than the old months-long feedback loop on a bad architectural decision, junior engineers today can, in principle, see the consequences of their own mistakes far sooner than developers historically could.
Pull quote
“You should spend several months in that state being horribly unproductive but learning a hell of a lot. And by the time you've gone through that gauntlet, maybe you can be trusted to run an agent of your own.”— Robert C. Martin
Worth noting
Martin repeatedly flags this section as speculative ("I don't have perfect answers to it because I really don't know") rather than a settled prescription.

Names and terms at a glance

Glossary & Entities

CRAP score — An acronym for a formula combining code coverage and cyclomatic complexity into a single 'how crappy is this function' score; Martin keeps it below 4 for human-written code and has widened the threshold to 6 (considering 8) for agent-written code.
Mutation testing — A technique that automatically flips operators in source code (e.g., < to >, = to !=) and re-runs the test suite for each flip, expecting a failure; a passing 'surviving mutant' flags a gap in test coverage.
Lost in the middle — An observed effect where content at the start and end of a model's context window retains priority/attention while content in the middle is effectively ignored as the window grows.
Smart zone / dumb zone — Dex Horthy's term (credited by Pocock) for the portion of a context window (roughly the first ~150k tokens) where a model reasons well, versus the later portion where attention becomes diluted and quality degrades.
Trajectory — Pocock's term for the persistent directional drift a context window develops once steered a certain way — later instructions in the same session keep bending toward that established direction, and only a fresh context clears it.
Tactical vs. strategic programming — A distinction credited to John Ousterhout: tactical programming is ground-level task execution (what agents are currently good at); strategic programming is directing the overall shape and architecture of a system (what agents are currently weak at).
Deep modules — John Ousterhout's concept of a module with a small, simple interface hiding a large amount of internal complexity, contrasted with 'shallow' modules that expose a wide interface with little hidden behind it.
