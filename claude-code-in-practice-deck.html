Start with codebase Q&A

  1. First use of an agent on a repo should be questions, not edits.
  2. It answers by exploring — grep, git log, linked issues — not by text search.
  3. Anthropic's technical onboarding went from 2-3 weeks to 2-3 days this way.
  4. Asking is how you learn what it one-shots and what needs hand-holding.
  5. Nothing is indexed or uploaded, so there is no setup step to wait through.

What to do

  • Make the first session on any unfamiliar repo a question session — edit nothing.
  • Ask about usage, not just definitions: how is this instantiated, where is this called.
  • Ask about history — why an argument exists, who added it, what issue it links to.
  • When onboarding a teammate, have them start here rather than with tools or edits.
  • Track which questions get one-shotted; that boundary is what tells you how to prompt.

Give it a way to check its work

Hand the agent something that can objectively score its own output — a test suite, a screenshot, a simulator — and it stops needing you between attempts, because it can tell for itself whether the last one was closer.

Give it a way to check its work

  1. One pass with no feedback signal gets you "pretty good" and stops there.
  2. An objective check — tests, screenshot, simulator — lets it grade its own attempt.
  3. Two or three self-graded iterations is where pretty good becomes almost perfect.
  4. The check must be machine-readable, not a matter of taste.
  5. Pick the check that fits the domain; any domain has one.

What to do

  • Before prompting, ask what would tell the agent it got this wrong — then wire it up.
  • Give UI work a screenshot tool (browser or simulator), not a written description.
  • Give logic work a test command it can run itself, not a request to be careful.
  • Say explicitly to iterate until the check passes, not to make one attempt.
  • Check in the tooling — an MCP server or script in the repo — so the loop is shared.

The context hierarchy

Agent context is not one file but a stack of scopes — enterprise, user, project, directory — and the useful question about any piece of context is which scope owns it and whether it loads every session or only on demand.

The context hierarchy

  1. A project CLAUDE.md is read into the first user turn of every session.
  2. The same scoping applies to commands, permissions and MCP config, not just memory.
  3. Enterprise scope sets policy users cannot override; local scope stays out of git.
  4. Nested files load only when the agent works in that directory — context on demand.
  5. Keep the always-loaded file short: it is paid for on every single request.
  6. Start with the shared project scope — written once, it benefits the whole team.

What to do

  • Put team-wide facts in the project file and check it in; keep personal ones local.
  • Move anything only relevant to one subtree into a CLAUDE.md inside that subtree.
  • Turn a repeated multi-step prompt into a slash command instead of always-loaded prose.
  • Use enterprise scope for pre-approved commands and hard blocks, not for advice.
  • Check in the MCP config so a teammate's first session already has the team's tools.
  • Re-read the always-loaded file periodically and cut anything not earning its tokens.

A super intelligent Unix utility

  1. Non-interactive mode takes a prompt and returns an answer, no session, no UI.
  2. Ask for JSON and the output is parseable by whatever runs next.
  3. It reads stdin, so anything you can pipe becomes its input.
  4. That makes it composable: CI steps, incident response, log triage.
  5. The allowed tool list is what makes an unattended run safe to leave alone.

What to do

  • Run the agent headless with a prompt argument the next time you would have opened a REPL for a one-shot question.
  • Ask for structured output whenever something downstream will read the result.
  • Pipe the input in rather than describing it — a log, a diff, a status output.
  • Pass an explicit allowed-tools list for anything running unattended.
  • Look at your existing scripts for a step that fails because it needs judgment; that step is the candidate.

One session, one assignment

Worktree-isolated sessions let several agents work at once without their changes mixing — but only if each session gets one clear job, or you end up with a pile of tangled work to sort out at the end of the day.

One session, one assignment

  1. Separate sessions, separate worktrees — changes stay isolated instead of mixing.
  2. One session, one clear assignment, one specific handoff format.
  3. Different job types in parallel: a bug fix, a copy change, a sales asset.
  4. The goal is small packets you can review, not one big pile to untangle.

What to do

  • Before starting parallel sessions, write one specific handoff format per session — what it should come back with, not just what it should do.
  • Mix job types across sessions (bug fix, copy, sales asset) rather than three variations on the same task — that's what actually benefits from isolation.
  • Review and merge each session's output separately; don't let three sessions' changes pile up before you look at any of them.

The ladder is the point

Every rung buys the next one. Questions teach you where the agent's competence ends, so you know what to delegate. A checkable target lets it close that gap itself, two or three iterations at a time. Context placed at the right scope makes the target correct without being re-explained every session. And an agent that needs neither your explanation nor your approval is one you can pipe, schedule, and run several of at once. Skipping to the last rung is how people end up with an expensive autocomplete.
