Shift the checkpoint left or right

  1. Plan, ship, review — the checkpoints are the human parts.
  2. Handing all three to AI at once is the wrong move.
  3. Big work: shift the checkpoint left, align before it starts.
  4. Small work: shift it right, review the diff at the end.

Your effort level is too high

  1. Higher effort means more thinking tokens for the same work.
  2. Exploration barely benefits from effort — it just costs more.
  3. Benchmarks hold the task static. You don't have to.
  4. Start at the lowest effort you have and crank up only if you need to.

Read the cost-quality curve

  1. Plot quality against average cost per task, not quality alone.
  2. Each model traces a curve as its effort level rises.
  3. The curve flattens — extra-high and max can be indistinguishable.
  4. The same score is often available far cheaper from another model.

Sacrifice grammar for concision

  1. Agents default to paragraphs. You have to read all of them.
  2. Ask for extreme concision, explicitly sacrificing grammar.
  3. You get headers, fragments and short lists instead of prose.
  4. Put it in the global config so it applies everywhere.

The code is the agent's environment

An agent's output quality is bounded by the codebase it works in, and unlike a human it has no memory to route around a bad one — so software fundamentals matter more now, not less.

The code is the agent's environment

  1. The codebase is the environment the agent operates in.
  2. A garbage codebase produces garbage output.
  3. Humans build a feel for a bad codebase. Agents cannot — no memory.
  4. So the same mistakes repeat, on dumb models and smart ones alike.

What to do

  • Judge a refactor by whether it makes the codebase easier for an agent to explore.
  • Put tests at seams that let an agent verify a change without understanding everything.
  • Encode the guardrails that stop repeated mistakes — the agent will not remember them.
  • Stop reaching for a smarter model when the real obstacle is the environment.

There is no such thing as greenfield

The only real difference between a greenfield and a brownfield codebase is that one has settled conventions and the other hasn't yet — and with an agent filling the repo, that distinction survives about a week.

There is no such thing as greenfield

  1. Everything is built for the real world, with real constraints.
  2. Brownfield means the conventions already exist, often only in the code.
  3. Greenfield just means you pick them — once.
  4. A repo goes from fresh to legacy faster than ever now.

What to do
