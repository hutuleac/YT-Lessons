Stop steering Claude: brief it, check it, and add only what it gets wrong

Most Claude Code advice from a year ago — plan first, think hard, write long rules, install skill packs — patched models that no longer ship. The current pattern inverts it: say what done looks like, give Claude a way to prove it, and only add infrastructure where it actually fails.

You've used Claude Code for months and your setup has grown by accretion — plan-mode habits, a long CLAUDE.md, a folder of skills — and you're not sure which of it still earns its tokens.

The ticket needs a visible finish line

A vague prompt makes the agent guess what matters, and once it's guessing you're no longer managing the work, you're cleaning it up — a real ticket names the scope and the finish line.

The failure mode isn't the agent's competence, it's the size and shape of what it was given. 'Make this pop' has no finish line, so the agent supplies one — its own guess at what matters — and a guess you didn't make is a guess you now have to check line by line. A ticket like 'add a waitlist form with name, email, company, and a success state, matching the current brand' has a scope an agent can actually finish and a reviewer can actually check against.

Greg Isenberg's version puts plan mode before the build: the agent inspects the repo, hands back the files it would touch, the smallest implementation, the risk, and what it is leaving out, and waits. Sized to one ticket, not a project plan (see The spec-driven development trap), so you have something concrete to react to.

That step has since been dropped by the person who invented it. Boris Cherny, who built Claude Code, said in January that most of his sessions started in plan mode; by autumn 2026 he said on Hacker News it is no longer useful. Plan mode never changed what Claude could do — it appended a reminder not to start coding yet, a fix for older models (Sonnet 4.6, early Opus) that jumped straight in. Newer models plan while they work, so his brief became three parts: the task, the guardrails around it, and what done looks like — then let the model work it out and check the result afterwards. For bigger changes he asks for a diagram or an interactive demo of what changed. Plan mode still exists and still earns its place on a model that dives in too early; it is no longer the default.

The definition of done is the part that compounds. It is the finish line the agent works toward, the thing you check the output against, and — written precisely enough — the check the agent can run on itself (Give it a way to check its work).

Ticket size is also what makes review possible. A tightly scoped ticket produces a diff you can actually read; a vague one produces a pile of changes that might look impressive but is hard to trust, because nothing bounded what got touched.

What to do

  • Write the ticket the way you'd brief a new hire: job, scope, expected experience, and what's off-limits — not "make it better."
  • Brief in three lines — task: this week's report from the CRM export; guardrails: don't amend the template, don't email anyone; done: every figure matches the export.
  • Reach for plan mode only when the model starts building before it understands the job.
  • When it finishes, ask for a one-page visual of what it did and what it assumed.
  • If a ticket is big enough that you can't review the diff in one sitting, it's not one ticket.

2 / 8 · builds on tokens

Your effort level is too high

Effort is thinking tokens spent per task, and the benchmarks that justify cranking it up hold the task fixed — but you can rewrite the task, and a better-specified task needs less effort.

Effort level controls how many reasoning tokens the agent spends. Crank it up and it thinks harder about the same work — including the parts that do not reward thinking. Exploring a codebase is the clearest case: it is a task you do not really need effort for, so extra effort mostly buys you a slower, more expensive traversal and an agent pushing hard on things that did not need pushing.

The benchmark charts do show quality rising with effort, and Pocock's objection to them is precise: those charts hold the task static. The task is a fixed prompt on a fixed problem. You, unlike the benchmark, can change how the task is specified.

That is the substitution worth understanding. High-quality information given to the agent up front does the work that reasoning tokens would otherwise have to do. The better the spec, the less effort the same job requires — so effort is a knob you reach for when your specification has run out, not the first thing you turn up.

The practical recommendation is to start at the lowest effort level you have access to and raise it from there. Not zero: some thinking tokens are worth having, because chain of thought is a genuinely useful way to work with agents.

The old in-prompt version of this dial is gone, per Simon Scrapes. Claude Code once mapped "think", "think hard", "think harder" and "ultrathink" to bigger thinking budgets; it now reads them as ordinary words, and effort is a separate setting with a recommended level per model. Simon Scrapes, relaying Anthropic, puts the default further up than Pocock does: Opus 5.5 recommends medium, and Anthropic says medium matches or beats Opus 5 on high for coding and knowledge work, so his advice is to leave it on the recommendation. The two disagree on the floor, not the direction — neither raises effort by default, and both treat a better-specified task as the thing that actually buys quality.

mediumOpus 5.5's recommended effort — which Anthropic says matches or beats Opus 5 on high for coding and knowledge work
The more high-quality information you give it, the lower effort you actually need to complete the task.

It turns effort from a quality dial into a symptom: if you need max effort for routine work, the specification is doing too little.

What to do

  • Start at the lowest effort level available and raise it only when output actually suffers.
  • Don't spend effort on exploration — spend it on the reasoning-heavy step, if any.
  • Improve the spec before raising the dial; information substitutes for thinking tokens.
  • Keep some thinking tokens — chain of thought is worth its cost.
  • Drop "think hard" / "ultrathink" from prompts — set effort in the setting instead.
  • If you don't want to tune it, leave it on the model's recommended level, never above.

Give it a way to check its work

Hand the agent something that can objectively score its own output — a test suite, a screenshot, a simulator — and it stops needing you between attempts, because it can tell for itself whether the last one was closer.

Boris, who built Claude Code, describes this as the workflow that separates a good result from a nearly correct one. Give the agent a mock and ask for the web UI and it gets close on the first attempt. The gap between close and right is not more instruction — it is more attempts, and attempts are only worth anything if something tells the agent which direction it moved in.

That something has to be objective. A unit test run, a Puppeteer screenshot of the page, a screenshot from the iOS simulator: each produces evidence the model can read back on the next turn and compare against the target. Without one, the agent has already emitted its best single guess, and asking it to try again just resamples the same guess. With one, it has a gradient — this failed, that passed, the layout is off by this much — and it can walk it without you in the loop. His number is two or three iterations to go from good to almost perfect.

The practical consequence is that setting up the check is the work. Whatever the domain is — unit tests, integration tests, browser screenshots, native app screenshots — the job is to hand the agent a way to see its own result, and then let it iterate. This is why a Puppeteer MCP server checked into a repo is worth more than any prompt written about the UI: it converts a single-shot request into a loop.

It is a narrower thing than having the agent judge a product as a user would. Taste questions — is this headline persuasive, is this flow confusing — are not oracles, because there is no pass/fail to read back. Those still need a human, or an explicit persona framing.

Two refinements since, both from Simon Scrapes. First, telling Claude to double-check in the prompt is now dead weight: per Anthropic's Opus 5 guide it already checks its own work unprompted, so the line adds cost without changing the result. What it cannot know unprompted is your pass/fail. Second, the check should come straight from the definition of done in the brief (The ticket needs a visible finish line). "Every figure matches the export" becomes a small check_report script that compares each figure and confirms every template section is filled: the first run fails on one figure, Claude fixes it, reruns, passes, and only then shows you — you read evidence instead of running the checks yourself. The check doesn't have to be code (a brand-voice doc a draft is graded against counts), but the more deterministic it is, the more it catches.

What to do

  • Before prompting, ask what would tell the agent it got this wrong — then wire it up.
  • Give UI work a screenshot tool (browser or simulator), not a written description.
  • Give logic work a test command it can run itself, not a request to be careful.
  • Say explicitly to iterate until the check passes, not to make one attempt.
  • Turn the brief's definition of done into the check — a script, or a doc the draft is graded against.
  • Don't write "double-check your work" — give it criteria it can pass or fail.
  • Check in the tooling — an MCP server or script in the repo — so the loop is shared.

4 / 8 · builds on checkable-oracle

The /goal judge only reads the chat

/goal keeps Claude taking turns until a separate small model rules the goal met — but that judge sees only the conversation, never your files or commands, so a goal it can't verify from the transcript ends the loop early.

A check Claude can run is only half of an unattended loop. The other half is something that keeps Claude going until the check passes — otherwise you sit there typing "continue" to get it to fix its own evidence. /goal is that half: after every turn, a separate small model reads the goal you set and decides whether the condition is met. If not, Claude takes another turn.

The catch is what the judge can see. It doesn't run commands or read files independently; it gets the conversation — your goal and Claude's output — and nothing else. So it can only rule on evidence that has been printed into the transcript. Set a goal like "the report is finished" and the only evidence available is Claude saying the report is finished, which the judge has no way to contradict. The loop stops on a claim, not a result.

That is why the goal has to name the proof, not just the end state. "The check_report script passes and you show me the output" forces the evidence into the chat where the judge can read it, and it ties the goal to the check written from your definition of done (Give it a way to check its work). Anthropic's guidance, as relayed in the video: one end state, how to prove it, what mustn't change, and a turn limit so a goal that can never be met doesn't run indefinitely.

The speaker frames this as how it works today, and hopes the explicit command goes away — that you'll eventually set the done criteria and the loop will simply run until they're validated. The judge-sees-only-the-transcript constraint is the part to check again before relying on it.

15turnsthe turn cap in the example goal — a stop condition, not a target

What to do

  • Write the goal as: end state, how to prove it, what mustn't change, turn cap.
  • Make the proof something printed into the chat — "show me the output" — not a file the judge will never open.
  • Point the goal at the check you already wrote, not at a description of being done.
  • Example: /goal check_report passes and you show me the output; the template is unchanged; stop after 15 turns.

5 / 8 · builds on context-hierarchy

CLAUDE.md is a contents page

CLAUDE.md should hold only what's always true and Claude can't work out — everything else becomes a pointer to a file Claude opens when it needs it.

Most instructions in an old CLAUDE.md were written to correct a model that no longer ships. Per the video, when Opus 5 shipped Anthropic deleted over 80% of Claude Code's own instructions for exactly that reason. The same audit applies to yours: a line that tells Claude to do what it already does is paid for on every request and makes the lines that matter easier to miss. Anthropic's docs, as the speaker cites them, already say to keep the file under 200 lines, because longer files cost more and get followed less.

The reframe is to treat CLAUDE.md the way SKILL.md works inside a skill folder: a contents page, not the content. Four kinds of line still earn a place — the tools and commands Claude can't guess, anything you do differently from how Claude would by default, gotchas it has got wrong more than once, and boundaries ("only write the email draft"). Everything else becomes a pointer to a file Claude opens only when the work calls for it — progressive disclosure, with CLAUDE.md holding only what's always true.

How the pointer is written decides whether that disclosure actually happens. An @-import loads the whole file into every session, which defeats the point; a path in backticks plus when to open it ("read docs/client-brief.md before any client work") lets Claude load it at the right moment. And per the speaker's reading of Anthropic's docs, a file reached only through another file gets its first 100 lines previewed, not read — so a chain of pointers silently truncates the detail at the end of it. Pointing to every file straight from CLAUDE.md, and putting a contents list at the top of anything over 100 lines, keeps a partial read from losing what matters. (Anthropic sets the contents-list rule for skill files; extending it to every file the index points at is the speaker's own practice.)

What to do

  • Delete every line Claude follows without being told.
  • Keep: commands it can't guess, your deviations, repeat gotchas, boundaries.
  • Write pointers as a backticked path plus when to open it — never an @-import.
  • Link every reference file straight from CLAUDE.md, not through another file.
  • Put a contents list at the top of any referenced file over 100 lines.
  • Run a prompt audit for stale-model instructions, dead paths and contradictions, and approve its cuts before it changes anything.

A skill is the corrections, not the process

Run the job without a skill first and write down only where Claude went wrong — those corrections are the skill, because anything Claude already does right costs tokens without changing the output.

A skill changes the output only where it tells Claude something it wouldn't have done on its own. Write a skill from the process in your head and most of it describes steps Claude already gets right — each one paid for in tokens, none of them moving the result. Anthropic's skill guide, as the speaker relays it, runs it the other way round: complete the task without a skill, run it on real tasks, and write down where it actually went wrong. The skill is then reverse-engineered from real failures rather than imagined ones, and Anthropic's team say most of their own best skills started as a few lines and a single gotcha.

The evidence that this matters is a placebo test. One developer (unnamed in the video) ran nine widely-starred skill packs — 450 runs on Opus 5.5, at the end of September — and only two of the nine beat a dummy file of the same length. The same-length dummy is the point: it controls for "any extra text changes behaviour," so what's left is whether the skill's content did anything. For seven of nine, it didn't.

Corrections are also model-specific. What a model gets wrong out of the box is a property of that model, so the skill has to be built on the model you'll actually run it on — another model will need more or fewer instructions. This refines rather than contradicts capturing a skill from one clean run (Skills, connectors, and hooks): capture from the run, but keep only the corrections that got it to your definition of done.

What to do

  • Do the job with Claude and no skill first; log every correction you make.
  • Write the skill from the corrections only — not from the process.
  • Build and test it on the model you'll actually run it on.
  • Run claude plugin eval with and without the skill; delete it if the scores match.
  • Run /skill-doctor to see what each skill costs and how often it fires; cut the unused ones first, then eval the rest.
  • Treat an installed skill pack as unproven until it beats no skill on your task.

7 / 8 · builds on context-window

The deterministic gauntlet

A long list of written rules loses its power, because the model forgets rules in the middle of the text. A tool that checks the code does not forget. Use a tool, not a long list of rules.

Uncle Bob's first method with agents was simple: write down the rules. His prompts grew into documents of five to ten pages. They covered test-driven development, clean code, and style. He wanted the agents to follow all of it. The agents read the rules. Then they did not follow the rules. His own words for this: the agents treat the rules "in the Pirates of the Caribbean sense — they're more like guidelines."

The cause is the same effect that shapes the whole context window. Text at the start and the end of a long prompt keeps the model's attention. Text in the middle does not. A long document buries most of its own rules. Rule fifty of a fifty-rule document has, in practice, no effect at all.

So he stopped writing long rule documents. His fix has two parts. First, cut the prompt down to the few words the agent must actually obey. Second, move every other rule out of the prompt and into a tool. He uses two tools for this: the CRAP score and mutation testing. The agent must run the tool and fix the code until the tool reports a pass. A tool sits outside the context window. It cannot get lost in the middle of a long document, because it is not part of the document.

This method costs time. Each check in the loop slows the agent down. He trades speed for quality, and he says he has not found the point where this trade stops paying off. But he has found a floor. Even with many checks, the agent still works about two to four times faster than he does by hand.

Shouting doesn't rescue a buried rule either. Writing IMPORTANT or MUST in capitals because the model kept missing something no longer works, per Simon Scrapes. In Claude Code the tool form of a must-never rule is a hook: a small script that runs at a moment you define — before every tool call, say — deterministically, spending no model tokens and firing whatever the model decided. "Never email the client" as a CLAUDE.md line is a request; as a hook that blocks any email to a client, it is a guarantee. That gives a mechanical audit: every all-caps line is either something Claude does anyway, so delete it, or something that must never happen, so make it a hook.

What to do

  • Keep the system prompt short. Use only the few sentences the agent must obey.
  • Put every other rule into a tool the agent must pass, not into a paragraph it might read.
  • Run the tool in a loop. Change the code until the tool passes, not until the agent says it is done.
  • Bring back checks you once rejected as too slow for a human. An agent does not mind the wait.
  • Search CLAUDE.md for anything in capitals. Delete it if Claude does it anyway; turn it into a hook if it must never happen.

Scheduled routines

Give an agent recurring, low-stakes responsibilities on a schedule — a morning brief, a weekly review — before ever letting it ship unsupervised, so the boring-but-essential work happens without you remembering to ask for it.

The instinct once an agent can run on a schedule is to reach for the most dramatic version — shipping code while you sleep. The safer and more useful starting point is the opposite: hand it the kind of recurring work that's low-stakes precisely because it doesn't touch production, but that a business quietly depends on someone doing — reading customer notes, noticing which issues keep coming up, deciding what's worth working on next.

A routine is that task, scoped and scheduled: read the customer and context folders, check open issues, write a summary to a specific file, with an explicit word cap and an explicit 'don't edit code, don't open a pull request.' The constraints are as load- bearing as the task — they're what makes a recurring agent safe to leave running unattended before you've built up trust in its judgment.

The payoff compounds because the routine's output feeds the rest of the system: a morning brief surfaces the day's highest-priority item before you've opened the repo, and a weekly review can catch a pattern — the same onboarding complaint from three different customers — that no single note would have surfaced on its own.

Two later changes widen what a routine can be. Triggers no longer have to be a clock: an event — a to-do added, a lead landing in the CRM — can start the work. And Claude Code projects now run as one ongoing conversation that spawns its own threads and keeps running with your machine off, so the isolated context a routine needs persists between runs. Simon Scrapes runs his whole social-content pipeline this way; his only step is approving the output. The low-stakes-first rule still applies — what changes is how much of the loop can run before it reaches you.

What to do

  • Start scheduled work with a read-only routine — no code edits, no pull requests — before trusting an agent with anything that ships.
  • Give every routine an explicit word or scope cap so it stays a brief, not a report.
  • Point routines at the same context folders the rest of the system already reads and writes to, so their output compounds instead of living in isolation.
  • Trigger routines on events (a new lead, a new to-do), not only on a schedule.
  • Keep your part to approving the output — that's the step that stays human.

Leave it alone until it fails

Every move here is the same move: give Claude the outcome and a way to prove it, watch where it actually goes wrong, and add infrastructure — a line in CLAUDE.md, a correction in a skill, a hook — only there. Re-run that audit each time the model changes, because the failures are a property of the model, not of your process.
