The context window

  1. The window is input plus output tokens — the whole thing, not one side.
  2. Every model has a hard limit and you get an error when you cross it.
  3. You can hit the limit mid-generation; the model can't route around its own ceiling.
  4. The bigger the window, the worse lost-in-the-middle gets.

What to do

  • Count the whole conversation against the limit, not just what you typed.
  • Put what matters at the start or the end; the middle is where attention thins.
  • Read a big advertised window as headroom, not as usable capacity.
  • Expect mid-generation failures on long replies and leave room for the output.

The dumb zone

  1. A 1M-token window is not 1M tokens of usable work.
  2. Add a token and the model tracks every relationship it has to every other token.
  3. Performance sinks gradually — there is no cliff, so nothing warns you.
  4. Rule of thumb: the dumb zone starts around 150k tokens.

What to do

  • Break work into small chunks and run each in a fresh context window — fewer tokens spent, better results.
  • Treat arrival in the dumb zone as a signal to clear, compact, or hand off to a new session.
  • Not every task needs the smart zone. Cheap, mechanical work can run in the dumb zone on purpose.
  • Redesign workflows so tasks don't need that much context in the first place.

Tool definitions are context

  1. The more tools you give an LLM, the worse it performs.
  2. A tool is not code to the model — it is a title, a description and a JSON schema.
  3. All of it sits in the system prompt, above everything else you sent.
  4. Six to eight is fine. Dozens fills the window before you have said anything.

Harness bloat

Kill the auto-memory

  1. Turn auto-memory off and delete what the agent saved itself.
  2. It is too eager: a one-off preference leaks into every later conversation.
  3. Stateless means a consistent base, so behaviour is predictable.
  4. Write preferences yourself, in a file you control.

Docs as a second source of truth

  1. Docs written to explain the code are not executable and not testable.
  2. So they drift, and now two sources of truth disagree.
  3. The agent can't tell which one is real — and it costs tokens to read both.
  4. Keep the docs code genuinely can't carry: decisions, glossary, a thin map.

What to do

  • Delete docs that restate the code — invest that effort in making the code readable instead.
  • Keep architecture decision records: alternatives considered are not recoverable from code.
  • Keep a glossary of domain terms; the agent cannot infer what your nouns mean.
  • Keep the navigational layer thin — a map, not a mirror.
